会员积分系统设计开发

Kody Joy2024-09-272024-09-29

前言

对每位做产品的人最直接的鼓励就是愿意为其买单。用户买单的方式多种多样，可以一次性买断，也可以订阅式付费进而享受持续的高级功能维护升级。这个功能点独立出来就是会员系统的设计开发，本文先不考虑支付手段的接入，重点关注会员功能的设计思路。

会员系统的设计与开发

用户类别设计

会员系统的核心是会员等级的设计。通常可以分为以下几个层次:

  • 免费用户：每天限量 10 次使用，角色值设为 0
  • 月度会员：每天可使用 500 次，角色值设为 2
  • 加油包用户：每次购买增加 100 次使用次数，不单独设角色值，所有角色均可购买

会员功能核心逻辑设计在于：

  • 免费用户可升级月度会员，周期 31 天
  • 会员可提前续费延长有效期
  • 用户使用次数受限后，通过加油包获取更多次数，加油包有效期 7 天，多次购买，有效期顺延

兼顾用户的轻度、重度和临时使用需求，结合定价策略，激励用户订阅月度会员。根据实际用户充值和反馈情况可继续调整。

数据存储设计

考虑到会员和加油包有过期时间，如果使用关系型数据库还需要定期去修改用户角色，为了便捷开发，在此使用 Redis 作为存储解决方案，只需给 Redis key 设置过期时间，key 过期等效于会员或加油包到期。

Redis 可使用 Upstash 的免费 Redis 资源，在数据存储的设计上，有几个关键的 Redis key

  • 用户每日已使用次数：userId:<userID>::date:<date>::user_date_uses
    • 用户每日第一次使用功能时，通过自增命令，Redis 会自动创建一个与日期相关的 key；
    • 有了每日使用的次数，我就可以通过用户角色对应的日上限（普通用户10次，会员500次）算出该用户每日剩余次数
    • 为什么我记录已使用次数，而不是记录剩余次数？这是因为，如果记录剩余次数，当剩余0次时会查询到0，而当天第一次使用前，查询剩余次数会因为 key 不存在而查到 null，在区分0和 null 的时候，可能会出现混淆，所以我认为记录已使用次数是更好的做法。
  • 会员状态：userId:<userID>::membership
    • 用户升级会员后，服务端会在 Redis 里创建这个用户的会员状态 key，value 设置为2，表示用户是有效的会员。
    • key 的过期时间是会员的剩余有效期（秒为单位）。
  • 加油包余额：userId:<userID>::boost_pack_uses
    • 用户购买加油包后，会创建一个初始 value 为100的加油包余额 key
    • key 的过期时间是加油包的有效期（秒为单位）
    • 当用户日限额用完后，开始扣加油包的余额，用 desc 进行自减

真实上线环境中，流程应该是查询订单状态，内部调用升级、续费、获得加油包的方式，本例仅作测试和演示，剥离支付功能，在此说明。

为了方便维护 Redis 相关的 key 和一些配置项，集中编写管理：

API接口开发

  1. 升级/续费会员：/api/membership/upgrade

upgrade 功能设计：

  • 判断用户角色
    • 普通用户，升级会员，设置 userId:<userID>::membership 的 value 为 2， 过期时间 31 天
    • 会员，延长会员期限，更新 userId:<userID>::membership 的值
  • 考虑增加情况当日已使用次数函数，每次用户充值则调用清空
  1. 购买加油包：/api/membership/buyBoostPack

bookstPack 功能设计：

  • 判断当前加油包剩余次数
    • 剩余 0，则设置为 100，过期时间设为 7 天
    • 剩余大于 0，则增加 100 次数，增加 7 天过期时间
  1. 检查会员状态和使用次数：/api/membership/checkStatus

checkStatus 功能设计

  • 获取userId:<userID>::date:<date>::user_date_uses、userId:<userID>:boost_pack_uses和userId:<userID>::membership的值，返回当前可用次数、加油包余额、加油包过期时间及会员过期时间
  1. 函数调用
  • 服务端调用方法前，先查询剩余次数，如果日剩余次数+加油包次数>0，则可以调用，否则返回错误信息

incrAfterUse 用来修改 redis 统计的使用次数，先判断日限额剩余次数，再判断加油包剩余次数

  • 默认使用次数 - 日使用次数 > 0, 则自增一个日使用次数
  • 默认使用次数 - 日使用次数 <=0，则判断加油包次userId:<userID>::boost_pack_uses 值
    • 大于 0，则自减 1

前端展示

本例仅作功能演示，界面集中展示会员有关状态信息和操作

  • 会员用户信息：展示当前会员状态、剩余次数、加油包余额（包括到期日期）以及会员到期时间等
  • 提供升级会员和购买加油包的操作按钮
  • 提供会员续费按钮
  • 增加模拟会员和加油包过期的按钮

提示和警告

  • 用户达使用限制后，提示会员续费或购买加油包
  • 加油包或会员即将过期时，做出相应提醒

风险应对策略

涉及到金钱的功能一定要做好风险应对策略，否则出了生产事故就会对品牌产生很大影响。本文核心逻辑都是在操作 redis，所以主要考虑 redis 的连接和操作失败的问题。因为这是一块很大的专题，所以不在本文进行详细叙述，仅抛砖引玉提供一些应对策略：

  • 重试策略：由于网络波动或短暂的服务中断，Redis 操作可能会偶尔失败。这种情况下，实施一个自动重试策略是有益的。
  • 错误日志：确保记录所有 Redis 相关的错误，这样你可以追踪、分析并修复它们。
  • 用户反馈：如果 Redis 操作失败，并且你已尝试了所有自动重试，那么应该给用户一个明确的错误消息。这样，用户会知道发生了什么，并且可以稍后重试。
  • 后备策略：考虑创建一个后端队列或延迟任务系统。当 Redis 操作失败并且重试不起作用时，你可以将操作的详细信息放入队列中，并在后台持续尝试，直到成功。
  • 监控：使用 Upstash 提供的监控工具或其他第三方服务，如 Datadog 或 Sentry 来实时监控 Redis 的性能和错误率。这样，如果出现问题，你可以迅速得知并采取行动。

结语

本文，我们探讨了会员积分系统的设计与开发，重点关注了系统的功能实现和用户体验。通过前端展示，用户能够清晰地查看自己的会员状态、剩余次数及加油包余额，并能方便地进行续费和升级操作。同时，我们也设计了相应的提示和警告机制，以确保用户在使用过程中不会错过重要信息。

在风险应对策略方面，我们强调了对用户使用限制的管理，确保系统的稳定性和用户的满意度。通过对核心功能的详细代码分析，我们展示了如何有效地获取用户状态、处理使用次数以及维护数据的准确性。
